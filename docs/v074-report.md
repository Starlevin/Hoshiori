# v0.7.4 森空岛签名故障修复与交接

日期：2026-11-02。版本0.7.4，versionCode14。应用标识、原签名、本机密钥和schema5沿用；不清账号或记录。

## 根因与设备证据

0.7.3修正设备缓存对象的id读取后，用户仍反馈第二个森空岛账号授权失效。这次在用户已连接的MuMu内，仅对尚未完成绑定的森空岛会话进行有限诊断：凭据始终留在应用进程，日志只含状态码、游戏数量及格式布尔值。没有发起签到请求。

同一会话以App和网页两套platform/vName上下文查询角色，均返回HTTP401、业务码10000。官方签名令牌续期返回HTTP200、业务码0，但原序列化方式仍得到10000。设备时钟与官方响应约差1至2秒。

关键差异来自Android框架的`org.json`：`JSONObject.quote`将设备标识中的正斜杠转义为`\/`，官方网页的`JSON.stringify`保留`/`。HMAC签名比较的是实际字符，两者语义相同也会签出不同结果。此前JVM测试使用的org.json实现没有相同行为，加上固定向量不含正斜杠，没能覆盖这一Android专属问题。

只将签名上下文恢复为网页相同的正斜杠表示后，仍使用原本存储的会话，两套上下文均返回HTTP200、业务码0和两个游戏分组。这证明本次拒绝不能只归因于“没登录”、模拟器或platform值。分组数量仍不等于最终绑定或签到成功。

## 实现与回归

新增`Signing.sklandContext`：按固定顺序构造platform、timestamp、dId、vName，保留必要的引号、反斜杠和控制字符转义，仅统一正斜杠表示。正式SklandAdapter调用此函数。未改变签到请求正文序列化，也未猜测更换UA、设备指纹或平台参数。

新增Android设备测试，使用含正斜杠的虚构设备标识，对照独立Python hmac/hashlib校验值；另测引号、反斜杠与换行保持转义。JVM适配器测试检查真实角色查询路径使用正确签名上下文。

设备真实会话诊断是显式启用的测试，常规CI不读取个人账号。只选择未完成的森空岛草稿，不能对已绑账号签到。后续正常绑定仍由用户确认游戏与角色。

## 验证结果与限制

本机JDK17、项目独立Gradle缓存构建，assembleDebug、testDebugUnitTest、assembleDebugAndroidTest、lintDebug均通过，耗时2分59秒。JVM160项通过，0失败；lint为0错误、22警告、2提示。

已保留数据覆盖安装MuMu Android15，设备读回0.7.4-debug/code14，首次安装时间仍为2026-11-02 15:21:47。两项Android签名回归测试，以及一项显式开启的正式适配器真实角色查询，共3项通过。正式适配器使用原本保存的待绑定会话读取到1个明日方舟角色、0个终末地角色。

随后实际点击账号页“继续读取角色”，经正常ViewModel→LocalSignEngine→SklandAdapter流程，页面显示“已从官方接口读取1个角色，请确认”，明日方舟真实角色可选，原“授权失效”消失。未替用户勾选身份核对或确认绑定，页面保留供用户确认；未发起签到。

这次已验证真实授权及角色读取恢复，但最终绑定仍待用户确认，真实签到未测试。0.7.3的23项导航/布局/渲染回归此前已通过，本次只有签名适配器修改，没有将旧结果冒充本版重复执行。长期令牌续期、后台与其他社区的全部实号场景尚未因此得到验证。前版功能及限制见[v0.7.2报告](v072-report.md)与[15项验收矩阵](v070-report.md)。

## 产物与后续复现

本地候选目录：`outputs/Hoshiori-v0.7.4-candidate/`，包含原签名可安装APK、SHA-256、构建信息、源码归档与本报告。设备截图及带有用户角色的UI层级只留在私有工作目录，不进入公开仓库。CI调试签名与本机不同，不要用CI包覆盖原安装。

普通回归可单独运行`SklandSigningAndroidTest`，不需要真实账号。`SklandSessionProbeTest`默认跳过，只有显式传入`skland_probe=true`才读取未完成的森空岛草稿；加`production_adapter=true`仅使用正式适配器查询角色。它不记录身份、令牌、角色名或角色ID，不提交签到。不要在用户输入中运行设备测试。
